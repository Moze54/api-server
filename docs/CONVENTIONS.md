# 接口开发规范（硬性）

> 适用范围：本仓库所有 HTTP 接口（现有与未来新增）。**新增/修改接口前必须通读本文。**
> 冲突裁决顺序：本文 > README > 个人偏好。不满足硬性条款的代码不允许合并/部署。

## 0. 优先级总纲

1. **接口响应速度 —— 第一优先级**
2. **接口稳定健壮 —— 第二优先级**
3. 其余一切（代码可读性、优雅、文档、可观测性）皆为次要，不得以牺牲前两条为代价换取。

判断口诀：**主流程上只留"必须现在做才能给出响应"的事；其他一切——能异步的异步、能缓存的缓存、能降级的降级。**

## 1. 响应速度（硬性）

### 1.1 主流程纪律

请求 goroutine 内**只允许**出现这五类工作：

1. 鉴权 / 限流判断（纯内存操作）
2. 参数校验与大小限制（在最便宜的环节拒绝非法输入）
3. 缓存查询（L1 内存优先）
4. 走并发闸门的上游调用（这是接口的本职工作）
5. 响应组装

**禁止出现在主流程**：

- 同步写数据库（访问日志、统计、缓存持久化等一律异步）
- 多个相互独立的可并行上游请求被串行调用
- 热路径上编译正则（必须包级预编译，`var xxxRe = regexp.MustCompile(...)`)
- 无上限的内存分配（读请求体必须 `LimitReader` 限长）
- 阻塞等待异步结果（异步投递必须非阻塞）

### 1.2 异步纪律（能异步尽异步）

- 可延迟的工作——访问日志、缓存 L2 落盘、过期清理、告警通知——**一律异步**
- 异步投递**必须非阻塞**：队列/信号量满则丢弃并计数，**宁可丢数据也不拖慢接口**
- 异步任务的失败只记日志/指标，绝不向上返回错误、绝不影响本次响应
- 服务关停时必须排空异步队列（`wg.Wait()` / channel drain）；丢弃量必须可量化（如关停时打日志）

### 1.3 上游调用纪律

- `context` 全程贯穿，超时由 `scraper.Pool` 统一约束，禁止裸 `http.Get`
- HTTP 客户端共享复用（keep-alive 连接池），**禁止**在请求路径上 new Client/Transport（每次多付 TLS 握手）
- 相互独立的多个上游请求**必须并行**（`sync.WaitGroup`），总延迟 = 较慢者而非总和
- 瞬态错误（网络抖动 / 5xx）重试一次，退避 ≥300ms；4xx 与调用方取消/超时不重试
- 缓存优先：相同请求必须命中缓存（TTL 见配置 `default_cache_ttl_seconds`）

### 1.4 性能红线

- 缓存命中路径：服务端处理 < 5ms
- 包装类接口：≤ 1s（上游自身耗时除外）
- 爬虫类接口：冷调用 ≤ 3s（受上游站点速度制约），热调用走缓存红线
- 热路径不得有 O(n²)；单请求内存分配必须有界

## 2. 稳定健壮（硬性）

### 2.1 故障隔离

- 所有上游任务必须走 `scraper.Pool`：并发信号量 + 单任务硬超时 + 排队上限（超排返回 42902）
- panic 由 Recovery 统一兜底返回 50000，**进程永不因单个接口倒下**
- 单个爬虫/适配器解析失败只影响其自身路由

### 2.2 降级优先于报错

- 多数据源：单源失败返回可用部分（参考 weather：预报页成功即成功，`current` 缺省）
- 能用旧缓存数据 > 直接报错（前提：语义上可接受旧数据）
- 双源全挂才返回业务错误

### 2.3 输入与资源上限

- 请求体 ≤ 1MB（统一走 `readBody` 限长）
- 缓存载荷上限：L1 ≤ 256KB、L2 ≤ 1MB，超限不缓存，防内存/库膨胀
- 队列长度、缓存条目数（L1 ≤ 1024）、并发数全部有常量上限
- 爬虫必须做 SSRF 防护：目标解析到内网/保留地址拒绝、跨域重定向禁止
- 客户端可注入的字段（如 X-Request-ID）必须白名单校验后采信

### 2.4 错误规范

- 一律业务码（`internal/resp` 常量），统一响应包 `resp.OK / resp.Fail`
- 对外消息不泄漏内部细节（堆栈、SQL、文件路径）
- 结构化错误：爬虫用 `scraper.Error`，厂商用 `provider.Error`，handler 统一映射

## 3. 参数简单（硬性）

- 输入 JSON 顶层字段 ≤ 5 个；所有非必填字段有默认值
- 必填缺失/非法 → 40001，错误消息必须告诉调用方"怎么改对"（带示例）
- 禁止深层嵌套结构，扁平 JSON 优先
- 命名与既有接口一致（`city`/`city_code`、`url`、`max_links` 风格）

## 4. 新增接口检查单（逐项全过才算完成）

- [ ] 任务走 `pool.Run`，ctx 贯穿到底
- [ ] 缓存 Get/Set 已接（自动继承两级缓存与 TTL）
- [ ] 主流程无同步落盘 / 同步写库 / 正则编译 / new HTTP Client
- [ ] 独立上游请求已并行化
- [ ] 错误映射到业务码；对外消息可指导调用方修正
- [ ] 输入校验 + 大小上限 +（爬虫类）SSRF 防护
- [ ] 单测固化上游返回格式（fixture），对方改版时测试会红
- [ ] `go vet ./... && go test ./...` 全绿
- [ ] 实测冷调用 + 热调用各一次并记录耗时（对齐 1.4 红线）
- [ ] `/api/v1/meta` 描述与 README 已更新

## 5. 现成设施（禁止重复造轮子）

| 需求 | 用 | 位置 |
|---|---|---|
| 统一响应 / 业务码 | `resp.OK / resp.Fail` | `internal/resp` |
| 两级缓存（L1 内存 + L2 SQLite） | `cache.Cache`，L2 异步落盘 | `internal/cache` |
| 并发闸门 + 超时 | `scraper.Pool.Run` | `internal/scraper/pool.go` |
| 鉴权 / 限流 / 访问日志 / panic 恢复 | middleware 链（main.go 注册一次，新接口自动继承） | `internal/middleware` |
| 业务错误类型 | `scraper.Error / provider.Error` | 各包 |
| 上游抓取模板（共享客户端+Referer+限长+重试） | `Weather.fetch / fetchRetry` | `spiders/weather.go` |

## 6. 已知的异步化取舍（知情决策，勿当 bug"修复"）

- 访问日志队列满会丢条目：计数、关停时告警 —— 换取接口零延迟
- 缓存 L2 异步落盘：极小概率丢"刚写完立即重启"的一条缓存 —— 换取写路径零阻塞
- `/api/v1/stats` 同步查询 DB：管理接口、仅 admin 密钥可用、`days ≤ 90` 上限，属可接受范围
